# v0.7.0 证据完整性重构报告

状态：`LOCALLY_VERIFIED / REAL_USER_ALPHA_PENDING`

产品版本：`0.7.0`

数据库：SQLite Schema 4

方法包：`law_full_recall_v1@0.3.0`

## 第一性原理

本轮没有继续扩张“智能”功能，而是重建学习证据成立所需的最小契约：

1. 一次学习证据必须绑定**当时的学习材料版本**，历史答案不能被后来编辑的正文重新解释。
2. 学习目标属于证据契约。同一正文从“精确复现”改为“适用”等目标变化后，旧掌握不能自动继承；只改标题不应制造新的证据版本。
3. 高置信法律关键冲突必须进入**有效证据裁决**，真实影响掌握状态、复习间隔和错因，不允许只停留在五维展示层。
4. 一条错误只有在新的、无提示、达到当前有效证据门槛且没有硬冲突的修复复测之后，才可以进入人工确认关闭。
5. 来源原文、可编辑学习单元、模型/启发式诊断和用户确认继续分层；系统不知道的语义应标记为待核验，不能伪装成正式法学判断。

## Schema 4：版本化证据契约

### KnowledgeUnit 当前状态

`knowledge_units` 新增：

- `body_hash`
- `source_basis_text`
- `source_basis_hash`
- `source_basis_status`

`source_basis_text` 用于保存来源基底快照，前端只读显示；可编辑的 `body` 明确称为学习单元文本。

### KnowledgeUnitVersion

新增 `knowledge_unit_versions`，每个证据版本保存：

- 单元版本号；
- 标题与学习正文；
- `body_hash`；
- 来源基底文本与哈希；
- 页码范围；
- `objective_type`；
- 快照状态与时间。

正文或学习目标变化才产生新的证据版本。标题独立修订不改变证据版本。

### StudySession 冻结材料

完整闭卷会话开始时保存：

- `unit_version`
- `unit_body_hash`
- `unit_snapshot_json`
- `snapshot_status`

会话后续展示、评分和历史查询优先使用被冻结快照。当前 KnowledgeUnit 后来变化，不会重写已经发生的会话材料。

活动完整闭卷期间禁止修改该知识单元的正文或学习目标，避免“A材料开始、B材料评分”的时序污染。

### Attempt 与 ReviewState

Attempt 保存其所属的单元版本、正文哈希和快照状态。ReviewState 也绑定精确 `knowledge_unit_version + unit_body_hash`。

只有当前知识单元版本与 Attempt 的证据契约一致时，Attempt 才能更新当前掌握状态。正文或学习目标改版后：

- 当前掌握状态失效；
- 新版本重新进入待学习队列；
- 与旧证据契约绑定的开放/修复中错误进入 `superseded`；
- 历史 Attempt 与会话继续保留旧快照；
- 正文变化会使派生卡片进入 `stale`。

## 有效证据裁决

新增 `app/services/evidence_integrity.py`，把 Provider 的原始覆盖分与真正参与掌握/调度的**有效学习证据分**分开。

当前裁决：

- `blocked_critical`：存在高置信法律关键冲突，有效分上限 45，掌握状态 `需立即修复`，立即到期；
- `blocked_structure`：回答结构明显不成立，有效分上限 55，掌握状态 `学习中`；
- `needs_verification`：存在可能冲突或方法包未完成，保留原始分作为信息，但当前掌握进入 `待核验`，短期复测；
- `accepted`：没有上述阻断，才进入现有可解释复习策略。

这层解决了 v0.6.0 中“界面已经发现关键冲突，但主评分仍100、ReviewState仍基本稳定”的跨层脱节。

## Legal Signals v2 硬化

关键冲突检测仍是保守的本地安全闸门，不是完整法律语义求解器。本轮增加：

- 双向句对扫描，降低“先写正确句再补相反结论”的漏检；
- 主体—动作—对象关系检测，例如债务人/债权人履行方向反转；
- 数字—期限—动作绑定，检测“30日通知、60日起诉”对调；
- 短规则保护，例如“合同无效”；
- 中文顿号、逗号、分号式关键词堆砌识别；
- 否定作用域保守分层：`并非无效`、`不当然无效` 等进入 possible/uncertain，而不是直接硬判相反。

硬冲突和可能冲突被分开。只有高置信 Hard Conflict 直接阻断掌握；复杂否定和不确定关系进入待语义核对。

## 错因修复门

`open → repairing → resolved` 继续保留，但 `can_resolve` 现在要求对应被冻结 repair session 的最新复测同时满足：

- `hint_level=0`；
- 有效证据分至少 70；
- 证据权重至少 0.99；
- `evidence_verdict.status == accepted`。

1分复测、关键冲突复测和待核验复测都不能解锁普通“确认已修复”。最后关闭仍由用户人工确认，因此当前系统只证明“满足本地证据门”，不证明实体法结论绝对正确。

## Schema 3 → 4 迁移边界

旧完整闭卷历史没有保存精确材料快照，迁移无法凭空恢复过去状态。因此：

- 使用迁移时可观察到的当前 KnowledgeUnit 回填旧 session 快照；
- 明确标记 `legacy_backfilled_current`，不得冒充精确历史；
- 对无法证明仍属于当前正文版本的旧 ReviewState 采取保守失效策略；
- 旧 RetrievalAttempt 的既有快照语义不改写。

回退 v0.6.0 或更早代码前应恢复 Schema 4 升级前的完整备份。

## UI 与目标身份信任边界

- KnowledgeUnit 审核器把“教材来源快照（只读）”和“学习单元文本（可编辑）”分开展示。
- 方法包反馈统一称为“五维学习目标恢复检查”。运行时根据 `body_hash` 与 `source_basis_hash` 标记 `source_exact / edited_learning_text / legacy_unverified / source_basis_pending`。
- 只有冻结学习目标与来源基底哈希完全一致时，`source_bounded=true`。人工改写目标仍然可以训练，但明确标记为“目标=人工改写学习文本”，避免把人工笔记冒充教材原文。
- 草稿知识单元默认必须先审核；后端也拒绝未显式批准的 draft 直接启动闭卷。
- 反馈主分显示“有效学习证据分”；如原始覆盖分被证据裁决压低，同时显示原始覆盖分，避免信息消失。
- 关键冲突现在确实会改变后端掌握状态与调度，前端“关键冲突会阻断”的提示与实际行为一致。

## 验证

当前工作树已执行：

```bash
python3 -m compileall -q app tests scripts
node --check app/static/app.js
pytest -q
python3 scripts/http_smoke.py
python3 scripts/backup_restore_smoke.py
python3 scripts/browser_smoke.py
python3 scripts/browser_ui_round2.py
python3 scripts/browser_real_e2e.py
```

结果：

- 36 项 pytest 通过；
- 真实 Uvicorn HTTP 主链通过；
- Schema 4 备份、破坏与恢复通过；
- Chromium Mock API 的桌面/移动端视觉与交互回归通过；
- 由于当前执行环境的 Chromium 策略阻止页面直接访问 localhost，新增 E2E 使用**真实 Chromium 页面 + 浏览器请求桥接到真实 Uvicorn/FastAPI**。桥接路径不返回 Mock API 数据，验证关键冲突从浏览器输入一直传到真实后端有效证据分、掌握状态和 ErrorRecord。

此验证不能冒充“浏览器直接 TCP 连接真实 localhost”；它证明的是 UI 逻辑与真实 FastAPI 的跨层语义接线。

## 当前仍然做不到

- 任意法律文本的完整语义正确性判断；
- 权威法条、司法解释、判例的自动效力核验；
- 完整争点识别与事实—要件涵摄；
- 精确段落/坐标级 PDF SourceChunk；
- 对所有中文否定作用域、指代和关系反转的完备解析；
- 跨题错误的深层语义根因聚类；
- 基于真实遗忘数据的个体化调度；
- 真题、案例题、选择题和论述题的成熟训练引擎。

因此 v0.7.0 的准确定位是：**版本化、可追溯的法学学习证据底座已经成立；法律语义智能层仍处于保守安全闸门和来源恢复阶段。**
